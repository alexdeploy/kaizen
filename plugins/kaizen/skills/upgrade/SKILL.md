# /kaizen:upgrade

Bring a project's kaizen-generated config up to the current plugin version
**without destroying anything the user changed**.

This is the skill that replaces `--force`. `--force` answers the question "what
if the templates changed?" with "overwrite and hope". This skill answers it with
evidence: it knows exactly what kaizen wrote last time, so it knows exactly what
the user has since made their own.

---

## The three states of every tracked file

`kaizen-lock status` classifies each file recorded at generation time:

| State | Meaning | What upgrade does |
|---|---|---|
| `unchanged` | Current content hashes to what kaizen wrote | Replace with the new version. Silent, safe, no question asked |
| `modified` | The user edited it | **3-way merge.** Never a blind overwrite |
| `deleted` | The user removed it | Leave it deleted. Mention it once; do not resurrect |

A file kaizen never recorded is **not kaizen's**. Do not touch it, ever, for any
reason, including when it sits at a path kaizen would normally generate.

---

## Arguments

| Arg | Meaning |
|---|---|
| *(none)* or `plan` | Analyse and print the upgrade plan. **Writes nothing.** |
| `status` | Just print the lock state (versions, per-file state). No template rendering. |
| `apply` | Execute the plan. The only mode that writes. Requires an explicit confirmation. |
| `--only=<paths>` | Restrict to a comma-separated list of paths. |
| `--dry-run` | With `apply`: do everything except the final writes, and report what would have happened. |

---

## Protocol

### 1. Read the lock

```
kaizen-lock status
```

Branch on the result:

- **`"lock_present": false`** → this project predates lock tracking (or was never
  set up by kaizen). Do **not** guess. Print:

  ```
  ✗ No lock file. This project's config was generated before kaizen tracked what it wrote
    (or was not generated by kaizen at all).

    Safe path forward:
      1. Commit or stash your current .claude/ so you can compare afterwards.
      2. Run /kaizen:init --force to regenerate and start tracking.
         Your current files will be overwritten — that is exactly why upgrade
         exists, and why this is the last time it can happen.

    Or, to adopt the current files as the baseline without regenerating:
      kaizen-lock write --plugin-version <current> <the files kaizen owns>
      ...then /kaizen:upgrade will work normally from here on.
  ```

  Stop. Never fall back to overwriting.

- **`"lock_present": true`** → continue.

### 2. Compare versions

Read `plugin_version` from the lock and the current plugin's `plugin.json`.

- Equal, and no file is `modified` → print `✓ Already up to date (<version>). Nothing to do.` and stop.
- Equal, but files are `modified` → this is a *drift* report, not an upgrade.
  Say so plainly: the templates have not changed, but N files have diverged from
  what kaizen wrote. Offer `status` detail. Do not merge anything.
- Lock version is **older** → this is the real upgrade path. Continue.
- Lock version is **newer** than the installed plugin → the user downgraded.
  Stop with a warning; do not "upgrade" backwards.

### 3. Render what the current templates would produce

For each tracked file, produce today's version **exactly the way `/kaizen:init`
would**: same preset, same profile, same placeholder substitution, same
enrichment directives. Read `profile` and `preset` from the lock so the
comparison is apples to apples — do not re-detect and silently change them.

Write each rendered file to a scratch path (e.g. `.claude/kaizen/upgrade-tmp/`)
so nothing lands in the project during planning.

### 4. Classify each file

For every tracked file, in this order:

1. **`deleted`** → skip. Add to the "left alone" list.
2. **`unchanged`** → compare rendered output against the current file.
   - Identical → nothing to do (do not report it as a change).
   - Different → **safe replace**.
3. **`modified`** → merge:

   ```
   kaizen-lock merge <path> .claude/kaizen/upgrade-tmp/<path>
   ```

   | Script result | Meaning | Plan entry |
   |---|---|---|
   | `"result": "clean"` | Both sides changed different lines | **auto-merge** — safe to apply |
   | `"result": "conflicts"` | Both sides changed the same lines | **conflict** — needs the user |
   | `"result": "no-baseline"` | Lock exists but the snapshot does not | **manual** — show a plain diff, never merge |
   | `"result": "deleted-by-user"` | File is gone | skip |

   Read the `merged_file` the script produced. Never merge by hand: the merge is
   `git merge-file`'s job, your job is deciding what to do with the result.

### 5. Print the plan

```
kaizen upgrade plan  ·  0.12.1 → 0.14.0

  Safe replaces (you never touched these)          3
    .claude/hooks/format-on-save.sh
    .claude/rules/testing.md
    .claude/agents/code-reviewer.md

  Auto-merges (your edits + new template, no overlap)   1
    CLAUDE.md
      + your "no moment.js" rule kept
      + new "Lint" command line added

  Conflicts (both sides changed the same lines)     1
    .claude/settings.json
      your value:   "defaultMode": "acceptEdits"
      new template: "defaultMode": "plan"

  Left alone                                        2
    .claude/hooks/session-start.sh   (you deleted it)
    .claude/rules/api-design.md      (yours, kaizen never wrote it)

Nothing has been written. To apply:
  /kaizen:upgrade apply
```

Rules for the plan:

- **Show the substance, not just the filename.** For merges, say in one line what
  survived and what arrived. A plan the user cannot evaluate is a plan they will
  approve blindly, which defeats the purpose.
- Never print a file with no changes.
- If every category is empty: `✓ Nothing to upgrade.`

### 6. Apply (only in `apply` mode)

1. **Refuse on a dirty git tree** unless the user insists: an upgrade the user
   cannot `git diff` afterwards is an upgrade they cannot review. Print
   `✗ Uncommitted changes present. Commit or stash first so you can review what upgrade did.`
2. Apply **safe replaces** and **auto-merges** by writing the rendered/merged
   content. `chmod +x` any shell script.
3. For **conflicts**, ask per file, one at a time, offering exactly three options:
   `keep yours` · `take the new template` · `write the file with conflict markers so you can resolve it`.
   Default to `keep yours` if the user is ambiguous. **Never resolve a conflict
   by judgement — the user's config is not yours to arbitrate.**
4. Re-record the lock for every file you wrote:
   ```
   kaizen-lock write --plugin-version <new> --profile <profile> --preset <preset> <files written>
   ```
   Files left alone keep their old entry; the script merges rather than replaces.
5. Delete `.claude/kaizen/upgrade-tmp/`.
6. Print a report in the same shape as the plan, past tense, plus:
   ```
   Review with:  git diff -- CLAUDE.md .claude/
   Undo with:    git checkout -- CLAUDE.md .claude/
   ```

---

## Hard rules (never violate)

- **NEVER write anything outside `apply` mode.** `plan` and `status` are read-only.
- **NEVER overwrite a `modified` file without merging.** No exceptions, no flags.
- **NEVER touch a file that is not in the lock.** If kaizen did not write it,
  kaizen does not own it.
- **NEVER resurrect a file the user deleted.**
- **NEVER resolve a conflict on the user's behalf.** Ask, or write markers.
- **NEVER auto-commit**, even after a clean upgrade.
- **NEVER re-run detection to change `profile` or `preset`.** An upgrade updates
  content, not identity. Changing profile is `/kaizen:init --profile=<new>`.
- If `kaizen-lock` is unavailable, stop. Do not improvise a fallback that writes.

---

## Failure modes

| Failure | Behaviour |
|---|---|
| No lock file | Stop with the adoption instructions from step 1. Never overwrite. |
| Lock file malformed | Stop. Print the path and the parse problem. Never guess. |
| Lock newer than installed plugin | Stop. The user downgraded; upgrading backwards would silently revert their config. |
| Baseline snapshot missing for a modified file | Mark `manual`, show a plain diff, never merge. |
| `git merge-file` unavailable | Stop. Merging is not something to approximate. |
| Rendering a template fails | Skip that file, mark it `unavailable` in the plan, continue with the rest. |
| Dirty git tree in `apply` | Refuse by default; proceed only if the user explicitly confirms. |

---

## Why this design

1. **Evidence over assumption.** The lock turns "did the user change this?" from
   a guess into a hash comparison. Every other decision in this skill follows
   from having that answer.
2. **`git merge-file` does the merging.** Merging is a solved problem with an
   implementation on every machine that has git. A model that merges by hand
   produces plausible-looking corruption — the worst possible failure for a tool
   whose promise is "does not break anything".
3. **Plan first, always.** The default invocation writes nothing. Trust in an
   updater is built by showing your work before doing it, every single time.
4. **Conflicts go to the user, not to judgement.** kaizen has opinions about
   defaults; it has no standing to overrule a deliberate change someone made in
   their own project.
5. **Deletion is a decision.** A user who removed a rule is telling you
   something. Re-adding it on upgrade is the single fastest way to make a tool
   feel hostile.
6. **This replaces `--force`, it does not complement it.** `--force` remains for
   the one legitimate case — a project with no lock that wants a clean
   regeneration — and should disappear once adoption is automatic.
